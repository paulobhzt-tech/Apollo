# P10.3 — plano de implantação futura, validação e reversão

**PLANO, NÃO EXECUTADO.** Não há autorização implícita de acesso, contratação, comandos remotos, DNS, certificados ou publicação. Executar futuramente somente os gates assinados no [checklist de autorização](P10.3-AUTHORIZATION.md). Nunca usar dados, URI, certificados, volumes ou segredos do site existente.

## Topologia decidida para planejamento

Preferência: VM temporária isolada, sem outros negócios, x86_64 compatível com o ensaio. Fluxo: navegador autorizado por IP/VPN → HTTPS `homolog.apollo-pdv.com:443` → proxy dedicado → Web P10 → Mongo exclusivo na rede privada. Um único worker Web, réplica Mongo **p10 de um membro**, autenticação, banco `apollo_p10_homolog`, usuário `p10_homolog` readWrite somente nesse banco. Um membro permite transações, mas não oferece failover/alta disponibilidade.

Não acrescentar Mongo público/Atlas ou ampliar o guard de hosts como atalho: isso mudaria o escopo aprovado. Não colocar Web ou Mongo na rede do site existente. Não expor 27017, 18082, 18443 ou a porta interna Web 10000 à Internet. O backend 10000 do container é distinto do Webmin 10000 do host.

### DNS e TLS — só após autorização específica

| Item | Decisão preparada | Prova exigida antes dos operadores |
|---|---|---|
| Nome | Somente `homolog.apollo-pdv.com` | Titular/administrador DNS identificado; nenhuma mudança no apex, e-mail ou outro site |
| A/AAAA | A para IP dedicado aprovado; AAAA somente se o caminho IPv6 estiver protegido e testado | Inventário anterior dos registros/TTL, resolução autoritativa e externa correta em ambos os protocolos |
| TTL | Proposta temporária 300 s, se compatível com o provedor | TTL anterior e plano de reversão registrados; cache DNS não reverte imediatamente |
| CAA/CDN | Inspecionar registro herdado e existência de proxy/CDN antes da escolha | Não alterar CAA do domínio inteiro nem habilitar CDN por conta própria; cadeia de IP confiável revisada |
| Certificado | Público válido, SAN somente do domínio de homologação; TLS 1.2/1.3 | Cadeia/hostname/validade verificados sem `-k`; chave privada restrita, fora do repo/app |
| Emissão | Preferir DNS-01 quando a aplicação ficar restrita por perímetro | Autorização DNS/TXT e método de renovação; segredo DNS no emissor separado, nunca no Apollo |
| Alternativa HTTP-01 | Expor exclusivamente o desafio ACME na porta 80; demais caminhos não encaminham à aplicação | Regra específica revisada, sem liberar SPA/API ao público para emitir certificado |
| Renovação | Cliente ACME/Virtualmin com responsável e alertas de validade | Ensaio suportado de renovação e certificado carregado; não assumir sucesso só por agendamento |
| HSTS | Escopo só deste host, inicialmente max-age=86400 conforme exemplo | Sem includeSubDomains/preload, sem afetar outros subdomínios |

HTTP-01 depende da porta 80; DNS-01 evita abrir o aplicativo para a validação. A capacidade do Virtualmin de automatizar DNS depende do controle/provedor de DNS suportado (fontes S2/S5 do diagnóstico). Não prometer automação antes de verificar a instalação. Toda emissão/renovação é ação externa e depende de autorização; nenhuma ocorreu aqui.

### Proxy e perímetro

1. Virtualmin/Apache: usar virtual server, usuário, document root/includes e logs **exclusivos**. O exemplo `deploy/p10/apache-virtualmin.conf.example` começa com `Require local`. Só substituir por IPs CIDR **dos testadores/VPN aprovados**, mantendo default deny; não usar `Require all granted`. O acesso restrito deve cobrir também menu público, QR e delivery durante homologação.
2. Preservar Host e definir esquema HTTPS no proxy; descartar `Forwarded`/X-Forwarded-For/Proto/Host fornecidos pelo cliente e gerar os corretos. Revisar mod_proxy/headers/remoteip/CDN efetivos. `TRUSTED_PROXY_IPS` só contém o peer real proxy/gateway (nunca `*`, nunca redes de clientes). Testar dois IPs e header forjado para confirmar orçamento por IP sem bypass.
3. Uma única origem SPA/API; `APP_URL=https://homolog.apollo-pdv.com`, `COOKIE_SECURE=true`, CORS vazio ou exatamente essa origem. Manter HttpOnly/SameSite e CSRF. Não aceitar certificado inválido ou desligar Secure para “fazer funcionar”.
4. Bloquear no proxy externo `/api/auth/first-access` após o bootstrap e confirmar a barreira backend. Não compartilhar cookie/jar de sessão entre testadores; credenciais únicas fictícias.
5. Proxy Nginx de `tls-test` é só modelo ensaiado em loopback; não é configuração pronta de borda pública. Revisar certificados, allowlist, default server/Host desconhecido, IPv6, logs e limites antes de converter para borda. Não subir um segundo proxy competindo com 80/443 do outro site.
6. No host Virtualmin, qualquer reload Apache pode afetar todos os vhosts: validar sintaxe, diff e baseline do site existente, ter reversão e autorização da janela. Não reiniciar serviços compartilhados. Se a integração exigir mudanças globais de rede/SELinux inseguras para o site, parar e usar host separado.

### Runtime e isolamento

Preservar os flags do env aprovado: homologation, DEMO, ACK sintético, integrações disabled, DB exclusivo, HTTPS e secrets file. **Não usar `APOLLO_P10_DISPOSABLE_RUNNER=1` no host humano persistente.** Gerar novos segredos com a ferramenta aprovada; não importar `.env` do desktop/VPS nem segredos de adquirente, SEFAZ, Drive, webhooks ou produção.

A rede Docker `private` é internal; Mongo não tem `ports`; Web publica só `127.0.0.1:18082`. Rever conflito da subnet e IPs confiáveis antes de criar qualquer rede. Manter nonroot/read-only/cap_drop/no-new-privileges, cache/limites testados. Não reduzir limites para caber na VPS. Não anexar API/Mongo à rede edge; proxy é o único componente de borda. O guard de egress é defesa adicional, não substitui firewall/rede.

SELinux permanece enforcing. Bind mounts/secrets terão diretórios novos, donos/contextos corretos e permissões restritas; revisar labels necessários no AlmaLinux. Nunca relabel do site existente, montar `/var/run/docker.sock` na Web ou desabilitar SELinux. Qualquer mudança de boolean global exige revisão e autorização, sem automatizar audit2allow.

O Compose base monta bootstrap_token permanentemente. Antes de expor, preparar um **arquivo runtime local revisado** que omita essa montagem, preserve a montagem individual de mongo_uri e mantenha todo o resto. Omitir/rotacionar token com acesso local controlado; confirmar endpoint não provisiona mais. Não presumir que uma lista `volumes` em override substitui a lista anterior: o merge Compose pode conservar a montagem. Inspecionar o modelo final sanitizado e mounts específicos, sem imprimir conteúdo secreto. Não foi criado nem aplicado override nesta missão.

Esta P10.3 não executa nem acrescenta workflow de deployment.

## Backup e restauração — plano verificável

Proposta sujeita ao titular: backup fictício antes/depois de cada sessão ou mudança, diário enquanto ambiente ativo, retenção inicial de sete dias, cópia criptografada fora do volume/host e descarte posterior autorizado. RPO/RTO devem ser preenchidos antes da janela; não foram medidos no destino nem existe agendamento implantado. Não usar integração Drive externa bloqueada como atalho.

1. Suspender novos testes e reconciliar sessão/estoque. Administrador exporta o JSON lógico `/api/backup` pelo canal autenticado; proteger arquivo e calcular SHA-256/manifesto. Não copiar cookie/senha para histórico do shell. O backup exclui sessões, hashes de senha/PIN, tokens externos e markers de segurança.
2. Registrar ID do backup, timestamp/fuso, versão/schema, commit, imagem, contagens, saldos, totais/estoque/lotes/contador e hash. Guardar chave de criptografia separada; testar que o responsável consegue recuperá-la. Backup lógico não é cópia da configuração do host/certificados; manter estes inventariados separadamente pelo titular.
3. Preparar **outro destino P10 vazio** com nova rede/volume e credenciais próprias; inicializar marker e identidade local. Nunca restaurar no banco do site, usar `drop`, limpar coleção do original ou executar `down -v` para liberar espaço.
4. Restaurar localmente usando o fluxo validado `lib.backups.restore_empty`, que valida formato/manifesto e usa transação. A API `/api/backup/restore` está bloqueada em homologação; não desligar o guard. Não há CLI operacional pronta de restauração no entrypoint P10: preparar/revisar o procedimento supervisionado e reproduzi-lo no ensaio isolado antes de A4. O teste automatizado de restore é evidência da função, não prova de um comando de operação inexistente.
5. Confirmar contagens/referências únicas/numeração, caixa, fiado, estoque/lotes, somatórios de movimentos e preservação do admin/markers **locais**. Contas restauradas não recebem senhas herdadas; provisionar acesso de teste no destino sob controle do responsável.
6. Registrar duração real e resultado; somente depois autorizar troca de destino. Não substituir dados fictícios divergentes para ocultar defeito. Fazer backup/restauração do outro site, se necessária à escolha da VPS, com o administrador desse site e autorização distinta.

## Rollback e condições de parada

Interromper entrada dos testadores se houver duplicação/divergência, confirmação financeira parcial, acesso indevido, segredo em resposta/log, egress externo, OOM/restarts/503 inesperados ou impacto no site existente. Fechar o **vhost/perímetro P10**, preservar log e estado incerto; nunca repetir venda com nova referência sem conciliar.

Reverter somente Web P10 à imagem anterior **aprovada e disponível**, preservando volume e compatibilidade de dados. Registrar último backup e operações desde ele. Se esta é a primeira publicação e não existe versão operacional anterior, rollback seguro é **retirar a P10 do ar**, não instalar uma versão arbitrária. Se schema/configuração incompatível, criar destino novo a partir de backup verificado e reconciliar; não fazer downgrade de banco nem apagar evidências.

Em Apache compartilhado, restaurar só o include/vhost P10 salvo, validar sintaxe e usar reload somente se expressamente autorizado. Não reiniciar o host, Apache/Mongo do outro site ou mudar daemon Docker/SELinux global como rollback automático. Reversão DNS restaura apenas os registros P10 anteriores e não elimina caches ou o serviço instantaneamente; fechar o perímetro primeiro.

O encerramento deve provar que o outro site manteve disponibilidade, P10 foi retirada/revertida, dados fictícios/evidências foram preservados e nenhum endpoint/volume ficou exposto. Destruição de VM, volumes, backups ou registros exige confirmação do escopo de descarte, nunca implícita em “rollback”.
